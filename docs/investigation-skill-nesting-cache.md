## 記事の主張

- Skillのネスト呼び出し(A→B→C)は展開形式(A+B+C統合)より1.7-3.1倍高コスト
- Prompt cachingはプレフィックス方式。途中に新コンテンツが入るとチェーン破断
- subagentは独立コンテキスト窓を持つ

## 検証結果

### 確認済み（正しい）

| 主張 | 根拠 |
|------|------|
| キャッシュはプレフィックス方式 | Anthropic公式docs: "Cache keys are cumulative" |
| Skill呼び出しがキャッシュを破断 | SkillはisMeta:trueユーザーメッセージを会話**途中に注入** |
| subagentは独立コンテキスト | 公式docs: "Each subagent runs in its own context window" |
| IN(New)/IN(Cached)はAPI指標 | cache_creation_input_tokens / cache_read_input_tokens |

### 我々のシステムには当てはまらない

**核心: SkillツールとReadツールは別物。**

| | Skillツール | Readツール |
|--|-----------|-----------|
| 動作 | 会話の**途中に**meta message注入 | 会話の**末尾に**tool_result追加 |
| キャッシュ影響 | **破断する** | **破断しない** |
| 記事の問題 | 該当する | 該当しない |

我々の「ネスト」（複数Read呼び出し）は:
- Readの結果はtool_resultとして会話末尾にappend
- プレフィックス（system, tools, 過去のmessages）は不変
- キャッシュチェーンは維持される
- 3ファイル個別Read ≠ 3倍コスト（フレーミングオーバーヘッドのみ: ~5-10%）

### 我々の忍者アーキテクチャ

記事が推奨するsubagent分離は、我々は既にプロセスレベルで実現済み:
- 各忍者は独立したClaude Code CLIインスタンス（tmuxペイン）
- 通信はファイルベース（inbox_write.sh）
- コンテキスト共有なし

## 改善施策の再評価

### P0: やる価値あり（理由は記事とは異なる）

| 施策 | 効果の理由（正しい根拠） |
|------|---------------------|
| cmd_152: 死んだcmdアーカイブ | コンテキスト窓の浪費防止（350行削減） |
| cmd_153: inboxアーカイブ | 同上（200+行削減） |

理由は「キャッシュ破断」ではなく「コンテキスト窓の物理的な空き容量の確保」。
Read内容がキャッシュされても、コンテキスト窓のサイズ制限には変わらない。
不要なコンテンツを読まないことで:
- compact頻度が減る
- 復帰時の再ロードコストが減る

### P1: 先送り（効果小）

| 施策 | 当初想定 | 実際 |
|------|---------|------|
| 報告バッチスキャン | キャッシュ破断8→1 | Read 8回のフレーミングOH削減のみ(~240tok) |
| PJ知識事前展開 | キャッシュ破断3→1 | 同上(~90tok) |
| karo.md安定化 | プレフィックス品質 | Readの前にsystem promptとして既に安定 |
| バッチデプロイ | Bash出力削減 | ~250行削減（軽微） |

P1以降は、コンテキスト窓に余裕がない場面（CTX>70%）でのみ検討する価値がある。
現時点では家老CTX 43%なので優先度は低い。

## 教訓

1. 外部記事の結論をそのまま適用するな。ツールの内部動作が異なれば結論も変わる
2. SkillツールとReadツールは根本的に異なる挙動をする
3. キャッシュ効率と窓容量は別問題。キャッシュされても窓は消費する
4. 我々のプロセスレベル分離（tmux独立ペイン）はsubagent以上の分離を実現済み
