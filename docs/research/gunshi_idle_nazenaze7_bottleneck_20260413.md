## なぜなぜ7回（v2: 重複投入の根因）

### 1. 何が起きた？
忍者3名が、軍師が既に完了した作業と同じ領域のcmdに投入された。

### 2. なぜ忍者が重複投入された？
家老がcmd配備時に「消火コードは軍師S181で既に撤去済み」と認識していなかった。

### 3. なぜ家老が認識していない？
軍師のidle自走成果がcmd配備判断に接続されていない。

### 4. なぜ接続されていない？
cmdと軍師/家老の自走は別系統。自走の結果が「cmdの前提を変えた」ことが伝播しない。

### 5. なぜ伝播しない？
軍師/家老の自走成果を「cmd相当の完了」として扱う仕組みがない。

### 6. なぜcmd相当として扱わない？
cmdフローが「将軍起案→忍者実行」の一本道で設計されている。

### 7. なぜ完了パスがない？（根因）
**cmdの完了パスが「忍者実行→報告→gate」の一本しかない。** 軍師/家老の自走能力が向上し、cmdスコープの作業を先に完了するケースが現実に発生するようになった。能力向上に管理系統が追いついていない。

## なぜなぜ7回（v3: GP-110 commit時hookの穴）

### 1. GP-110(commit時hook)に穴がある。なぜ？
commit時にpending cmdがまだ存在しない場合がある。

### 2. なぜ存在しない？
cmdの起案とコード変更は非同期。軍師がcommitした後に将軍が同じスコープのcmdを起案するケースがある。

### 3. なぜ後発cmdを検知できない？
hookはステートレス。commit時の一点で発火→消える。後から来るcmdを知らない。

### 4. なぜステートレスで問題？
git log(変更事実)とcmdフロー(作業計画)が別世界。commit時の一点接続では時間軸を跨げない。

### 5. なぜ時間軸を跨げない？
hookは「イベント発生時」の一点判定。タイムラグのある2つのイベント(commit vs cmd配備)を接続するには、**状態を持つ仕組み**または**後発イベント側でのチェック**が必要。

### 6. なぜ後発側チェックが正解？
git log自体が状態を持っている。配備時(deploy_task.sh)にgit logを見れば「対象ファイルに直近の非忍者commitがあるか」が分かる。新しい状態管理不要。

### 7. **なぜこれが構造的に正しい？**
配備=「これから忍者にやらせる」意思決定の瞬間。その瞬間に「既にやられていないか」を確認するのが最も自然なタイミング。commit時(前方)ではなく配備時(後方)にチェックすることで、タイムラグに依存しない。

## 確定対策: GP-110修正版（殿承認済み）

**deploy_task.sh内に配備前重複チェックを追加。**

```
配備直前にtarget_pathの直近commitをgit log -1で確認
→ 忍者以外(軍師/家老)のcommitが直近24h以内に存在
→ WARN「このファイルは{agent}が{hash}で変更済み。配備不要の可能性」
```

- ステートレス（git logが状態保持）
- タイムラグ無関係（配備の瞬間にgit logを見る）
- 既存インフラに1チェック追加のみ
- 家老にcmd起票依頼済み
