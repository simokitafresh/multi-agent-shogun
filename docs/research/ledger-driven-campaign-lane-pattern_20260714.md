- 起案: 殿指示 2026-07-14 22:40「この仕組みは他にも応用できるな。ドキュメントにまとめて今後も違うものにも応用するための基盤を作ろう」

- 正本: 本ファイル。索引: `context/semantic-map.md` alias「自走攻略レーン」

## §1 パターンの本質（1行）

**一次計測台帳が弾を選び、idle忍者が弾を撃ち、計測結果が次の弾を決める閉ループ。** 人（将軍・家老）の判断は「レーンの立ち上げ」と「裁定」だけに縮小され、個別タスクの起票・配備・優先順位付けは環境が行う。

```
一次計測台帳 ──優先選定──▶ タスク自動生成(品質契約焼込) ──idle検知──▶ 自動配備
     ▲                                                              │
     └──── 計測還流(after実測・re-enqueue・飽和検知) ◀── 実装→レビュー→GATE ──┘
```

## §3 構成要素（6要素の抽象形）

| # | 要素 | 実装例（テスト側レーン） | 汎用化の要点 |
|---|---|---|---|
| 1 | 一次計測台帳 | logs/test_timing_ledger.tsv（run_tests.sh自動追記） | **書き手が自動**であること。手動更新台帳はstaleで死ぬ（テスト時間免疫系の教訓） |
| 2 | 優先選定 | 閾値超wall降順+回帰WARN | 選定根拠（実測値・軸）をタスクへ記録し検証可能に。**単純順次（ファイル名順）は無優先＝効果順にならない** |
| 3 | 品質契約テンプレ | FAIL0・SKIP0・期待値緩和禁止・支配項実測→改修の順序・機能痩せ禁止(LS081) | 契約はタスク本文へ焼き込む。忍者に届くのはtask YAMLのみ（LS-A04(45)） |

| 5 | 安全ガード4種 | (a)idle限定配備 (b)completed再配備防止 (c)in-flight同一target直列化 (d)deploy契約充足（estimated_minutes等） | **4種とも初日の実戦で穴として発現した**。新レーンでは最初から入れよ（§7） |

## §4 適用条件（このパターンが効く対象・効かない対象）

**効く対象（4条件を全て満たす）**:
1. 対象群が機械的に列挙可能（ファイル一覧・台帳・カタログ）
2. 一次計測で優先順位付け可能（時間・件数・率などの数値）
3. 1タスクが忍者1名・短時間（deploy契約内）で完結
4. 成果が二値検証可能（before/after実測・PASS/FAIL）

**効かない対象（レーン化するな）**:
- 設計判断・裁定を要する作業（殿・将軍の領域）
- 本番SEALED操作（承認の鎖が必須。LS-A04(45)）
- 成果が主観評価の作業（二値化できない）

## §6 新レーン立ち上げ手順（テンプレ）

1. **台帳の確認/定義**: 自動書き手を持つ一次計測台帳を特定（なければ通常業務への相乗り追記を先に作る。専用計測runは作らない＝「検査のための検査」禁止・殿裁定07-14 01:41）
2. **優先選定の実装**: 閾値/軸を定数化し、選定根拠をタスクへ記録
3. **生成器の実装**: 品質契約焼き込みテンプレ＋deploy契約（estimated_minutes・split_decision等）を満たすtask YAML生成
4. **monitor接続**: 既存idle検知経路と同型で接続。既存レーンとの優先順位を明記
5. **安全ガード4種**: §3-5を最初から実装（後追いだと初日に穴が全部発現する）
6. **初弾実機確認**: 自動生成→配備到達→GATE CLEARの一巡を実機で二値確認
7. **fp計測接続**: 配備イベントをgate_fire_log→detector_fp_rateへ接続（誤選定を発報後に計測・削減）

## §8 三層学習ループとの対応

- 第一層（個）: 忍者の二値報告（改善なしも数値で正直に）＝飽和信号の源泉
- 第二層（対）: 将軍検分→家老hotfixの還流（本日3穴を即日補強）
- 第三層（全）: このパターン文書＝レーンの型自体を環境に埋め、次の対象へ複製可能にする
