## §0 本質（1行）

**一次計測台帳が弾を選び、idle忍者が弾を撃ち、計測結果が次の弾を決める閉ループ。** 人（将軍・家老）の判断は「レーンの立ち上げ」と「裁定」だけに縮小され、個別タスクの起票・配備・優先順位付けは環境が行う。

```
一次計測台帳 ──優先選定──▶ タスク自動生成(品質契約焼込) ──idle検知──▶ 自動配備
     ▲                                                              │
     └──── 計測還流(after実測・re-enqueue・飽和検知) ◀── 実装→レビュー→GATE ──┘
```

## §1 AsIs / ToBe

### AsIs（レーン以前の姿 — 2026-07-14朝まで）

| 側面 | AsIs |
|---|---|
| 弾の選定 | 将軍・家老がその都度判断。効果順にならず、思いついた順・目についた順 |
| 起票・配備 | 1タスクごとに将軍cmd起票→家老分解→配備。20本なら20回の人手 |
| idle資源 | 忍者のidle時間は修行サイクル頼み。攻略対象との紐付けなし |
| 計測 | before/afterは各忍者の報告文中に散在。横断集計・回帰検知が不能 |
| 終了判断 | 「もう十分か」を人が感覚で判断。飽和（改善なし反復）を検知できない |

### ToBe（レーン稼働後の姿 — 実測で到達済み + 残課題）

| 側面 | ToBe | 到達状況 |
|---|---|---|
| 弾の選定 | 台帳の実測値降順+回帰WARNで自動選定。選定根拠がタスクに記録される | ✅ 稼働（2レーン） |
| 起票・配備 | 生成器が品質契約焼込のtask YAMLを自動生成、idle検知で自動配備。人手ゼロ | ✅ 稼働（20本超/夜、手書きゼロ） |

## §2 5W1H

- **WHY（なぜこの型か）**: idle=最大の無駄（殿原則）。かつ人手の起票・配備は20本/夜のスループットに構造的に追随できない。判断を「型の立ち上げ」に一回だけ払い、以後は環境が回す=自動化×強制の適用形。
- **WHAT（何を作るか）**: 6要素（§3）を持つ閉ループ。①自動書き手つき一次計測台帳 ②優先選定 ③品質契約焼込テンプレ ④idle自動配備 ⑤安全ガード ⑥計測還流+飽和終端。
- **WHO（誰が何をするか）**: 将軍=レーン起票と検分。家老=生成器・monitor接続の実装配備と完了処理。軍師=レビューとボトルネック特定（例: CTX81%の一次特定）。忍者=弾の実装と二値報告（改善なしも数値で正直に）。環境=それ以外の全て。
- **WHEN（いつ動くか）**: 忍者idle検知の瞬間に常時。レーンは殿・将軍の在席と無関係に朝まで自走する（07-14夜実証）。
- **WHERE（どこに実装するか）**: 既存経路への相乗りのみ。台帳=既存runnerの自動追記、配備=ninja_monitor既存idle検知（_handle_speed_training_auto_deploy同型）、契約=deploy_task既存ゲート。**新しい箱を作らない**。
- **HOW（どう立ち上げるか）**: §6の7手順。安全ガードとfp計測接続を最初から入れる（後追いだと初日に穴が全部発現する=§5で実証）。

## §4 適用条件

**効く対象（4条件を全て満たす）**:
1. 対象群が機械的に列挙可能（ファイル一覧・台帳・カタログ）
2. 一次計測で優先順位付け可能（時間・件数・率などの数値）
3. 1タスクが忍者1名・短時間（deploy契約内）で完結
4. 成果が二値検証可能（before/after実測・PASS/FAIL）

**効かない対象（レーン化するな）**:
- 設計判断・裁定を要する作業（殿・将軍の領域）
- 本番SEALED操作（承認の鎖が必須。LS-A04(45)）
- 成果が主観評価の作業（二値化できない）

## §6 新レーン立ち上げ手順（テンプレ）

1. **台帳の確認/定義**: 自動書き手を持つ一次計測台帳を特定（なければ通常業務への相乗り追記を先に作る。専用計測runは作らない＝「検査のための検査」禁止・殿裁定07-14 01:41）。**全実行経路が台帳を通るかを最初に列挙**（穴7）
2. **優先選定の実装**: 閾値/軸を定数化し、選定根拠をタスクへ記録
3. **生成器の実装**: 品質契約焼込テンプレ＋deploy契約を満たすtask YAML生成。契約検査は生成・保存時に左シフト（穴1・cmd_3933）
4. **monitor接続**: 既存idle検知経路と同型で接続。既存レーンとの優先順位を明記
5. **安全ガード**: §5の穴1-6対処を最初から実装
6. **初弾実機確認**: 自動生成→配備到達→GATE CLEAR→**台帳追記**の一巡を実機で二値確認（追記確認まで含める。穴7）
7. **fp計測接続**: 配備イベントをgate_fire_log→detector_fp_rateへ接続し、**fp_rate100%検出は即是正cmd化**（穴9=削る側の実働）

## §6.5 連続トライ（multi-round）仕様 — 3者協議合意（2026-07-15 03:56、殿裁可待ち）

**発端**: 殿提案03:53「1弾1回で終わりは機会損失+トークン無駄遣い。2〜3回連続で改善トライさせよ」。1配備1改善のv2.0設計は、忍者が対象を読み込んだCTX資産をround 1で捨てていた。

**合意仕様（家老の適応型を骨格に将軍・軍師が補強）**:

| 項目 | 仕様 | 根拠 |
|---|---|---|
| round数 | **min_rounds=2 / max_rounds=3** | 軍師実測: 1回目=大改善(50-90%減が多数)、2回目=残余(5-10%)、3回目=限界的。min2は「1回目悪化」の修正機会を保証 |
| 時間予算 | **campaign_budget=10分/弾**、各round 5分以内 | R3は「budget内かつ次の支配項が特定済み」の場合のみ |
| **baseline継承** | **best_so_far**（直前afterではない） | **偽改善防止の本質**: 悪化runのafterを継ぐと「元へ戻すだけ」が改善に見える。実例=insight_write 13.0→15.2s悪化(+17%)。軍師初期案「直前after継承」はこの穴があり将軍指摘で修正 |
| 悪化run | **自動不採用**（差分/commitを採用状態にしない）、次roundはlast-goodから開始 | 計測の誠実さ(LS-A24)。悪化の正直記録は残す（飽和信号として価値がある） |
| 単位 | round別に**別task_id・別commit・別report** | rollback可能性+FAIL時の切り戻し単位を最小化 |
| 台帳 | generator ledgerへround_index / best_wall / last_wall / approach / stop_reasonを永続化 | 停止理由の分布が次のレーン設計の一次データになる |
| 終了条件 | (a)min2完了後に次支配項なし (b)budget到達 (c)max3 (d)FAIL/SKIP発生 | 「もう十分か」を人でなく条件が判定 |
| CTX管理 | R2完了後にCTX≥70%なら/clear+台帳注入で強くてニューゲーム | 軍師実測: 1修行≈30%CTX。3round=90%の断絶リスクを条項で吸収 |
| 実装AC必須 | **偽改善防止テスト**: R1 10秒→悪化15秒、R2 12秒でも「best 10秒を超えないため改善扱いしない」ケースを固定 | 家老最終指摘。仕様の核をテストで凍結 |

**効果見込み**: 家老の配備タッチポイント round数分→1（50-66%減）、対象読込CTXの再利用でトークン効率向上、悪化の成果化ゼロ。

**上位原則（§5穴5の一般化）**: multi-round化するとbaseline管理が「前回値」から「**最良値の系譜**」に変わる。roundを跨ぐ計測は必ずbest_so_farと比較せよ——「直前との比較」はround数が増えるほど偽改善の余地を広げる。
