## §2 なぜなぜ7回

### なぜ1: なぜCDP計測に4回かかったか？
→ cmd_2268(1回目)とcmd_2271(2回目)が失敗した。各失敗の根因が異なる。

### なぜ2: なぜcmd_2268が失敗したか？
→ (a) retry runを複数走らせてartifactが上書きされた(L649事故)
→ (b) GitHub Actions不在でCI PASS検証不能
→ **根因: retry runのartifact管理が未設計。同一ファイルに複数runが書き込む構造**

### なぜ3: なぜcmd_2271が2.5時間もかかったか？
→ (a) 認証方式の試行錯誤(viewer→admin Cookie→ドメイン設定誤り)
→ (b) 新スクリプト(measure_cmd2271.py)を独自作成(174行のscope外コード)
→ (c) Cookie設定修正→再実行→PF切替全SKIP→修正→まだダメ
→ **根因: perf_measure.pyの認証制約を理解せず独自スクリプトを作成。scope外暴走**

### なぜ4: なぜ忍者がperf_measure.pyの認証制約を理解しなかったか？
→ (a) cmd_2271時点でL650(viewer認証専用)が未登録(cmd_2268の教訓がまだ教訓化されていなかった)
→ (b) CDP教訓が0件注入された(deploy_task.shのtag matchがtarget_path=outputs/で非マッチ)
→ **根因: 教訓注入の精度不足(GP-223/225/226で修正済み) + 教訓登録の遅延**

### なぜ5: なぜcmd_2262(ベースライン)は28分で成功したのにretryは失敗するのか？
→ ベースライン計測は「初めての計測」で既存artifact/認証状態が白紙。retry計測は既存状態(前回のartifact/認証/設定)の影響を受ける。
→ **根因: CDP計測が冪等でない。前回の状態をクリーンアップする手順がない**

### なぜ6: なぜCDP計測の冪等性が担保されていないのか？
→ perf_measure.pyは結果をoutputs/に保存するが、前回結果の退避/分離はユーザー(cmd)の責任。
→ 認証セッションの有効性確認も事前チェックなし。認証が通らなければ計測が途中まで進んで失敗。
→ **根因: CDP計測のpre-flight check(認証確認+artifact退避)が存在しない**

### なぜ7: なぜpre-flight checkがないのか？
→ perf_measure.pyは元々手動ツールとして開発された。忍者が自動実行する前提の設計になっていない。
→ 認証確認→計測→結果保存→比較の一連のフローが1スクリプトに統合されておらず、各ステップを忍者が手動で判断する必要がある。
→ **根因: CDP計測パイプラインが「道具」として未成熟。忍者の判断力に依存する構造**

## §3 因果鎖

```
perf_measure.pyが手動ツール設計(why7)
  → pre-flight check不在(why6)
  → 冪等性未担保(why5)
  → 認証失敗に気づかず計測開始 + artifact競合(why2,3)
  → 教訓注入0件で忍者が独自スクリプト作成(why4)
  → scope外174行改変 + 2.5時間浪費(why3)
  → 4回実行で10.5時間消費(why1)
  → 殿の時間を10時間奪った
```
