# 三層長期外部記憶システム 運用原則
<!-- created: 2026-06-03 | source: lord conceptual review | status: design-principles -->

## §1 本質

三層記憶の目的は、大量の情報を保存することではない。
目的は、情報を長期的に使える記憶へ変換し続けることである。

この基盤は、LLMに一時文脈を渡す補助機構ではない。
人間とLLMが共有する、長期記憶、意味索引、知識編集、履歴管理、想起制御、再評価のための外部認知基盤である。

検索は入口の一つであり、中心ではない。
中心は、記憶を保存し、育て、修正し、想起制御し、再構成することである。

## §2 三層の役割分担

| 層 | 役割 | 守るべき境界 |
|---|---|---|
| SQLite全文記憶DB | 機械可読な記憶台帳。原文、断片、履歴、状態、参照関係、検索対象を保持する | 原文と加工物を混ぜない。検索スコアを信頼度にしない |
| Obsidian | 人間可読な認知編集層。概念ノート、判断履歴、研究ノート、MOC、リンク構造、解釈を保持する | 全量同期しない。自動生成物で読めない森にしない |
| セマンティック辞書 | 意味正規化・語彙展開・概念接続層。表記揺れ、同義語、上位/下位概念、個人語彙を管理する | 何でも関連づけない。混ぜてはいけない概念を明示する |

SQLiteは記憶の台帳である。
Obsidianは思考の編集環境である。
セマンティック辞書は意味の橋である。
LLMは補助者である。
人間は編集者、監査者、最終判断者である。

## §3 記憶として成立する条件

記憶は本文だけでは足りない。
長期的に使える記憶には、少なくとも以下が必要である。

- 出典
- 取り込み日時
- 更新日時
- 発生日時、観測日時、記録日時、訂正日時
- 現在も有効かどうか
- 事実、主張、仮説、解釈、判断、好み、方針、過去状態の区別
- 他の記憶との関係
- 人間が読んで再利用できる導線
- LLMが誤解しにくい粒度とメタデータ
- 失効、隔離、低優先度化、昇格の状態
- 訂正履歴とロールバック可能性

### timestamp原則

殿は、すべてにtimestampを明確にし、因果の流れを過去未来に辿れることを重視する。
三層記憶では、本文、派生物、関係、状態変更、訂正、昇格、失効、想起制御のすべてに時点を持たせる。

最低限、以下を分ける。

| timestamp | 意味 |
|---|---|
| occurred_at | 出来事が実際に起きた時点 |
| observed_at | 人間/エージェントが観測した時点 |
| recorded_at | SQLite/Obsidian/semantic indexへ記録した時点 |
| updated_at | 記憶本体またはメタデータを更新した時点 |
| validated_at | 検証・人間確認した時点 |
| invalidated_at | 失効・反証・誤情報化した時点 |
| superseded_at | 後続知識に置き換えられた時点 |
| archived_at | 現在知識から退避した時点 |

時系列が曖昧な記憶は、因果確認に使ってはいけない。
timestamp不明の場合は `timestamp_unknown` として扱い、現在知識への昇格を保留する。

因果リンクもtimestampを持つ。
`A -> B -> C` はリンク文字列だけでは不十分であり、A/B/Cそれぞれの時点と、リンクを作成・確認した時点を残す。
これにより、過去から未来への発展だけでなく、未来の反証から過去の前提へ遡る監査が可能になる。

## §4 SQLite記憶DBの設計原則

SQLiteは保存先ではなく、記憶の状態管理システムである。

### 持つべきメタデータ

- raw text
- extracted facts
- summary
- interpretation
- source
- ingested_at / updated_at
- occurred_at / observed_at / recorded_at / validated_at / invalidated_at / superseded_at / archived_at
- event_type
- tags / concepts
- linked Obsidian note
- linked semantic concept
- reference_count / last_referenced
- confidence
- freshness / expires_at
- state
- contradiction_candidate
- duplicate_candidate
- supersedes / superseded_by

### 状態の例

- raw
- extracted
- summarized
- interpreted
- unreviewed
- needs_review
- verified
- trusted
- stale_candidate
- expired
- false_info
- hypothesis
- refuted
- canonical
- historical
- archived
- deletion_candidate

### 原文と加工物の分離

原文は改変しない。
要約、抽出、解釈、分類、タグ付けは派生物として別管理する。
派生物には、生成元、生成時刻、生成処理、確認時刻を持たせる。

LLM要約や解釈は便利だが、原文ではない。
原文、要約、解釈、判断、仮説が混ざると、あとから一次情報と加工情報を分離できなくなる。

## §5 Obsidianの設計原則

Obsidianは全情報置き場ではない。
人間があとから読んで意味を再利用できる知識だけを昇格する。

### Obsidianに置くもの

- 概念ノート
- MOC
- 研究ノート
- 判断履歴
- 仮説
- 反省
- 失敗ログ
- 自分なりの定義
- 重要文献の要約
- プロジェクトごとの知識地図
- SQLite内の原文群への導線
- セマンティック辞書上の重要概念への導線

### 昇格条件

- 何度も参照された
- 人間が重要指定した
- 複数の記憶と関係する
- 概念ノートとして再利用できる
- 判断履歴として残す価値がある
- 研究テーマに関係する
- SQLite内の原文群を束ねる役割がある

Obsidianを自動生成ノートで埋めない。
Obsidianの価値は、情報量ではなく、人間が思考を再開できる構造にある。

## §6 セマンティック辞書の設計原則

セマンティック辞書は類語辞典ではない。
文字列、概念、文脈、個人語彙のズレを吸収する意味変換層である。

関係種別を明示する。

| relation | 意味 |
|---|---|
| same_as | 同一概念 |
| synonym_of | 同義語 |
| spelling_variant_of | 表記揺れ |
| abbreviation_of | 略語 |
| parent_of / child_of | 上位/下位 |
| broader_than / narrower_than | 広い/狭い概念 |
| related_to | 関連するが置換不可 |
| opposite_of | 反対概念 |
| often_confused_with | 混同されやすい |
| used_in_project_as | 特定PJ内での用法 |
| deprecated_term_for / current_term_for | 旧称/現行名 |
| should_not_merge_with | 混ぜてはいけない概念 |

意味検索は広げる方向に強い。
長期記憶では、分ける能力が同じくらい重要である。

## §7 記憶の階層

| 層 | 内容 | 注意 |
|---|---|---|
| Raw | 原文、ログ、引用、一次情報 | 改変しない |
| Extracted | 事実、日付、数値、人物、組織、主張、関係 | 原文への参照を持つ |
| Summary | LLM/人間の要約 | 原文の代替にしない |
| Interpretation | 解釈、仮説、評価、考察 | 事実と分ける |
| Canonical | 現時点で最も信頼する統合知識 | 回答に使う候補 |
| Historical | 古い判断、過去仮説、失効情報 | 現在知識と分ける |
| Personal | 価値観、判断基準、好み、研究上の癖 | 一般事実と混ぜない |
| Operational | タスク、TODO、処理履歴、プロジェクト状態 | 知識ノートと分ける |

この階層がないと、LLMは過去の仮説を現在の事実として扱う。

## §8 自動成長の原則

自動成長とは、情報を自動で増やすことではない。
新しい情報が入るたびに、既存の記憶体系が少しずつ良くなることである。

自動処理が行うべきこと:

- 関連候補の生成
- 重複候補の生成
- 矛盾候補の生成
- 失効候補の生成
- セマンティック辞書追加候補の生成
- Obsidian昇格候補の生成
- 重要記憶の昇格候補の生成
- 不要記憶の圧縮候補の生成
- MOC再構成候補の生成

自動処理が確定してはいけないこと:

- 原文削除
- 記憶の完全統合
- 現在知識への昇格
- 信頼度の最終判断
- 矛盾の最終解決
- セマンティック辞書への無条件追加
- Obsidianノートの無制限生成
- 人間の判断履歴の上書き
- 重要記憶の削除

成功条件は完全自動化ではない。
人間が少ない労力で質の高い判断を下せるようにすることである。

## §9 忘却ではなく想起制御とメンテナンス

timestampが明確なら、人間のような物理的忘却は原則として不要である。
SQLite/ファイル/Obsidianの外部記憶は、人間の脳のような容量制約を前提にしない。

したがって、本システムで「忘却」と呼んでいたものは、削除ではなく想起制御である。
古い記憶を消すのではなく、いつの記憶かを明示し、現在知識として使うか、Historical層として参照するか、通常検索で強く出すかを制御する。

削除は例外であり、原則は保持する。

- 完全削除
- アーカイブ
- 低優先度化
- 通常検索から除外
- 要約のみ保持
- 原文のみ保持
- Obsidianから外す
- SQLiteには履歴として残す
- 現在知識から外し、Historical層へ移す

このうち、通常運用の基本は完全削除ではなく以下である。

- timestampにより古さを明示する
- 現在知識からHistorical層へ降格する
- 通常検索の重みを下げる
- 回答生成時の採用候補から外す
- 必要なときは時系列・因果リンクで過去情報として辿れるようにする

完全削除は、重複生成物、破損データ、機密・安全上の理由、明確な保存禁止対象などに限定する。

棚卸し対象:

- 重複統合
- 古い情報の失効判定
- 誤情報の隔離
- 仮説と確定情報の分離
- Obsidianリンク切れ修復
- セマンティック辞書の剪定
- タグ体系の再編成
- 検索ログ分析
- 使われない記憶の圧縮
- よく使われる記憶の昇格
- LLM生成物と一次情報の分離

## §10 信頼度・鮮度・重要度

信頼度、鮮度、重要度、検索関連度は別物である。

### 信頼度の軸

- 出典の信頼性
- 情報の新しさ
- 人間確認の有無
- 複数ソース確認の有無
- 自分の経験との整合性
- 過去の使用実績
- 反証の有無
- LLM生成物かどうか
- 一次情報かどうか

### 重要度の軸

- 参照頻度
- 最終参照日時
- 手動重要指定
- プロジェクト関連度
- 判断への影響度
- 被リンク数
- Obsidian中心性
- セマンティック辞書上の概念中心性
- 過去に役立った実績
- 失うと困る度合い

古いから消すのではない。
古いので現在知識としては使わない、という扱いが必要である。

## §11 矛盾の扱い

矛盾を見つけたら、すぐ片方を削除しない。
まず矛盾の種類を分類する。

- 片方が誤情報
- 片方が古い
- 文脈が違う
- 定義が違う
- 分野が違う
- 時点が違う
- 観測条件が違う
- 意見が違う
- 仮説同士が競合している
- 過去判断と現在判断が違う

矛盾は `contradiction_candidate` として記録し、時点、出典、定義、現在有効な記憶、Historical層へ移す判断を残す。

## §12 自動要約の注意点

要約は原文の代替ではない。
要約は原文への入口である。

要約には以下を持たせる。

- 原文参照
- 生成日時
- 生成モデル/処理
- 人間確認有無
- 粒度
- 目的
- 省略された可能性のある情報
- 原文リンク
- 再生成履歴

要約は用途別に分ける。
検索用、意思決定用、Obsidian用、概念抽出用を混ぜない。

## §13 よくある失敗パターン

| 失敗 | 結果 | 対策 |
|---|---|---|
| 何でも保存する | 検索可能なゴミ屋敷になる | 種類、出典、状態、有効期限、重要度を付ける |
| Obsidianへ全量同期する | 人間が読めない森になる | 昇格条件を設ける |
| セマンティック辞書を自動追加し続ける | 意味空間が過剰接続になる | 関係種別、適用範囲、使用頻度、人間確認を持たせる |
| LLM要約を原文代替にする | 誤要約が一次情報扱いされる | 原文と要約を分離する |
| 古い情報を現在知識として扱う | 判断を誤る | 有効期限、失効状態、Historical層を持つ |
| 仮説と事実を混ぜる | 何を信じてよいか分からなくなる | Fact/Claim/Hypothesis/Interpretation/Decisionを分ける |
| 自動統合で元情報を消す | 誤統合時に戻れない | 原文保持、履歴保持、ロールバック可能性を必須にする |
| リンクを増やしすぎる | リンクの意味が薄くなる | リンクには種類と理由を持たせる |
| 検索スコアを信頼度と混同する | よく出る情報を正しいと誤認する | 関連度、信頼度、重要度、鮮度を分離する |
| メンテナンスを後回しにする | 全体が重く信用できなくなる | 想起制御、統合、失効、剪定を機能として扱う |

### 使用パターン確認の方法

殿に質問する前に、以下を確認する。

1. 直近会話で、殿が記憶DB・Obsidian・セマンティック辞書に何を期待しているかを抽出する。
2. 記憶DB検索・semantic_searchの呼び出し履歴から、検索語、ヒット有無、検索時間、再検索有無を集める。
3. 検索で見つからなかった概念、見つかったが使われなかった結果、古いが上位に出た結果を分類する。
4. 上記から「殿に確認すべき質問」を作る。質問はデータで狭めてから行う。

殿に聞く質問は、抽象的な「何が欲しいか」ではなく、以下の形にする。

- 現状検索で十分な具体例はどれか。
- 現状検索で不足した具体例はどれか。
- timestampは発生時刻、記録時刻、失効時刻のどれが最初に必要か。
- Obsidianへ昇格したいのは、よく使う記憶、判断履歴、概念ノートのどれか。

### 三層間同期コストの設計項目

同期パイプラインごとに以下を明記する。

| パイプライン | トリガー | 頻度 | 失敗時fallback | 人間確認 |
|---|---|---|---|---|
| SQLite→Obsidian昇格 | 参照頻度、手動重要指定、複数記憶の束ね役、判断履歴化 | 定期または明示実行 | SQLiteに候補状態で残す | 昇格確定前に必要 |
| Obsidian→セマンティック辞書候補 | 概念ノート更新、MOC更新、混同注意の追加 | ノート更新時または定期 | 候補のみ保持 | relation正式採用前に必要 |
| セマンティック辞書→SQLite検索適用 | relation追加、should_not_merge_with追加、検索ログ分析 | relation更新時 | 古い検索展開へ戻す | high-impact relationは必要 |
| 検索ログ→記憶メンテナンス | no-hit、ノイズ、古い結果上位、再検索 | 常時記録、定期集計 | ログだけ保持 | 修正・昇格・検索除外時に必要 |

## §15 レビュー統合結果（2026-06-03）

### 軍師レビュー（初回）

判定: confidence HIGH。timestamp原則、三層役割分担、自動成長境界は妥当。

追加指摘:

1. 検索ログ収集の仕組みが不足している。
   §9で棚卸し対象にするだけでは遅い。検索ログを収集しなければ、見つからない概念、ノイズ記憶、検索上位の古い記憶を改善できない。
2. Obsidian↔SQLite同期パイプラインが不足している。
   Obsidian昇格条件だけでは運用が手動に残る。昇格候補生成、確認、リンク作成、SQLite対応関係更新の流れが必要。
3. `should_not_merge_with` が実装優先順位に入っていない。
   長期記憶では検索漏れ削減だけでなく、誤結合を防ぐ能力が必要である。

### 将軍レビュー

現物確認結果: 現在のeventsテーブルはイベント蓄積としては機能しているが、殿の「記憶運用装置」には未達。

6大ギャップ:

| 優先度 | 原則 | 現状 | 必要な変更 |
|---|---|---|---|
| 1 | 記憶の状態管理 | eventsにstatus/state列がない | state列を追加し、未整理/確認済み/失効/仮説等を表現する |
| 2 | 原文と加工物の分離 | summary/detailに原文・要約・解釈が混在 | 原文、抽出、要約、解釈、判断を派生関係として分ける |
| 3 | 信頼度と有効期限 | confidence/expires_at/source_typeがない | 多軸信頼度、鮮度、有効期限、情報種別を追加する |
| 4 | セマンティック辞書の関係種別 | aliases平坦リスト中心 | same_as / parent_of / related_to / should_not_merge_with等を型として扱う |
| 5 | 矛盾候補 | contradiction_candidate機構なし | 矛盾を削除でなく候補として保存する |
| 6 | 段階的な想起制御 | archive/done化中心 | 検索除外、低優先度化、Historical層移動を追加する |

### 統合結論

設計原則は妥当。
次に必要なのは、三層記憶を「保存装置」から「記憶運用装置」へ進める実装設計である。

ただし、追加レビューにより、最初の実装単位を即断するのは早期終了だと判明した。
timestamp付き状態管理は有力な最初の実装候補だが、実装前に以下を確定する。

- 殿の使用パターンでは何が最初に不足しているか。
- 現行DB/Obsidian/semantic辞書と設計要求の距離はどれだけか。
- 三層間同期の頻度、トリガー、失敗時fallback、人間確認コストは許容できるか。

理由は、状態と時点がなければ原文分離、信頼度、想起制御、矛盾解決、Obsidian昇格のすべてが現在有効か判断できない一方で、殿の実使用に照らさない全量timestamp実装は過剰投資になりうるためである。
