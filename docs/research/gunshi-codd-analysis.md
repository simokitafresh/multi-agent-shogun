# CoDD (Coherence-Driven Development) vs 将軍システム分析

> 軍師分析 2026-03-29（v4: 実コード比較+定量データ検証済み）。将軍consultation依頼に基づく。
> 出典: zenn.dev/shio_shoppaize/articles/shogun-codd-coherence (おしお @shio_shoppaize)
> リポジトリ: github.com/yohey-w/codd-dev (MIT)

## §1 CoDD核心3行

- 設計書にfrontmatter(`depends_on`)で依存グラフを宣言
- 変更時に`codd impact`でGreen(自動修正可)/Amber(要レビュー)/Gray(情報)に分類
- Wave順(上流→下流)で生成、逆順(下流→上流)で影響分析

## §1.5 実装の全体像（全8モジュール+skills検証 v3）

| モジュール | 状態 | 実装内容 |
|-----------|------|---------|
| scanner.py | **安定** | 2フェーズスキャン(.md frontmatter + ソースimport正規表現) |
| graph.py | **安定** | CEGデータ構造+Noisy-OR信頼度統合+BFS伝播+JSONL永続化 |
| propagate.py | **安定** | git diff→ノード解決→BFS(max_depth=10)→Green/Amber/Gray分類 |
| validator.py | **安定** | DFS循環依存検出+dangling ref検出+severity分類(ERROR/BLOCKED/WARNING) |
| generator.py | **実装済** | wave_config→依存解決→AIプロンプト構築(禁止事項+必須セクション+convention)→出力sanitization+検証 |
| verifier.py | **実装済** | tsc+Jest実行→`@generated-from`ヘッダーで失敗→設計書トレーサビリティ(TypeScript特化) |
| implementer.py | **実装済** | Sprint別コード生成。設計書→AIプロンプト→ファイル出力。`@generated-by`追跡。先行タスク重複排除 |
| extractor.py | **実装済** | 多言語(Py/TS/Java/Go)静的解析→設計書逆生成。confidence 0.5-0.85。上限0.85=人間レビュー必須 |
| skills/codd-impact | **実装済** | **Green=AI自動修正**/Amber=人間承認制/Convention=最優先チェック |

**v2からの修正**: 「Wave生成/V-Model検証/自動修正は未実装」は誤り。全て実装済み。
初回分析でgraph.py/propagate.py/scanner.pyの3ファイルのみ見て結論した（想像するな確認せよ違反）。

### 注目すべき実装パターン
- **`@generated-from`トレーサビリティ**: 生成ファイルに出自を埋め込み→失敗時に設計書まで自動追跡
- **信頼度スコア**: frontmatter=0.9。Green帯域=≥0.90+evidence≥2。extractorのbrowfnield=0.5基本値+evidence加算(上限0.85)
- **Convention alerts最優先**: impact skill内でconvention違反をGreen/Amber/Grayより先にチェック
- **generator AIプロンプト**: 禁止事項(frontmatter出力禁止/TODO禁止)+必須セクション+convention引用+依存文書verbatim注入
- **extractor「事実のみ」哲学**: 推測せず正規表現確実マッチのみ。多言語統一インターフェース

## §2 我が軍が既にCoDD的に解決済みの領域

**結論**: 生成・実行フェーズは高カバー。**変更時の整合性維持**が未解決。

## §4 最小コスト最大効果の一手 — データ検証後の修正

### v2提案（撤回）: frontmatter依存宣言+impact gate
→ 解くべき問題（context整合性破壊）が実データで確認されなかった。ROI不成立。

### v3提案: `@generated-from`トレーサビリティパターンの採用

CoDD実装で最も我が軍に転用価値が高いのは、依存グラフではなく**出自追跡**。

**現状の問題**: gate/hookスクリプトが自動生成されるが、「どの教訓/PIから生まれたか」のトレースが人間記憶に依存。
- 例: `pre-bash-yaml-dump-guard.sh`がどのcmd/教訓から生まれたかを知るには、gitログかlessonsを人力検索する必要がある

**提案**: 自動生成gate/hookの先頭に出自コメントを自動埋め込み
```bash
# @source-lesson: L-YamlDumpDataLoss (cmd_1399)
# @source-pi: PI-018
# @generated-by: lesson_write.sh
```

**効果**: GATE FAIL時に「この防御はなぜ存在するか」を即座に追跡可能。教訓の退役判定にも活用。
**コスト**: lesson_write.sh + gate生成スクリプトに1行追加。既存コードの小修正。
**実データ裏付け**: gate_fire_log.yamlにFAIL理由は記録されるが出自教訓は未記録。

## §5 吸収すべきパターン vs 不要な部分

### 吸収すべきパターン

| パターン | CoDD実装 | 我が軍への適用案 |
|----------|---------|----------------|

| extractor「事実のみ」哲学 | 推測せず正規表現確実マッチのみ抽出 | 偵察cmdの品質基準に通じる。既に偵察5要件で実現 |
| 依存グラフ+impact分析 | frontmatter→BFS→3帯域 | §4の提案参照 |

### 採用不要な部分

| CoDD機能 | 不採用理由 |
|----------|-----------|
| `codd generate`(設計書自動生成) | 我が軍のcmdは殿↔将軍の対話から生まれる。自動生成は学習機会を奪う |
| `codd-dev` CLI直接導入 | ソフトウェア開発PJ向け(TS特化verifier等)。我が軍の運用知識基盤にはオーバースペック |
| `codd implement`(Sprint別コード生成) | 我が軍のimplは忍者が手動実装+学習ループ。AIコード生成は品質至上原則に反する |
| Noisy-OR信頼度計算 | 知識基盤20-30ファイル規模。二値(影響あり/なし)で十分。BFS+confidence計算は過剰 |

## §5.5 競合ツール比較（将軍調査補完）

将軍がOpenSpec/cc-spec-drivenも調査中。4ツールの位置づけ:
- **Spec Kit**(GitHub公式): 仕様駆動の標準化。「最初にどう書くか」
- **OpenSpec**: 軽量仕様フレームワーク。Spec Kitの軽量版
- **CoDD**: 「変更後の整合性をどう保つか」。唯一変更伝播に焦点。**実装は記事以上に充実**(全8モジュール実装済み)
- **cc-spec-driven**(mkhrdev): Claude Code特化のspec-driven workflow

我が軍への示唆: ツール直接導入は不要だが、CoDDの実装品質は高く原理・パターンの吸収価値あり

## §6 原理の本質と我が軍への接続

CoDD原理の本質 = **「変更が怖くなくなる」**
我が軍の免疫系 = **「失敗が怖くなくなる」**

両者は補完的:
- 免疫系: 失敗→分析→gate/hook→同クラスの失敗を永続防御
- CoDD的整合性: 変更→影響分析→自動伝播→知識基盤の整合性を永続維持

**統合ビジョン**: 免疫系(失敗防御) + 依存グラフ(変更追跡) = 知識基盤が変更にも失敗にも強いシステム

## §7 なぜなぜ記録 — 分析品質の自己検証

### 初回分析の誤り
「Wave生成/V-Model検証/自動修正は未実装」→ 全て実装済みだった。

### なぜ誤った？
1. graph.py/propagate.py/scanner.pyの3ファイルだけで結論した
2. cli.pyが7+モジュールに委譲する構造を確認しなかった
3. 「実験的」ラベルを「空スタブ」と想像した（確認していない）
4. GitHubディレクトリ一覧だけ見て中身を読まなかった(skills/, hooks/)

### 根因
**「想像するな確認せよ」原則の違反。** 2つのレベルで発生:
1. **コード探索**: 3ファイルで全モジュール構成を推論。generator.pyを読めば10秒で判明する事実を想像で埋めた
2. **ギャップ分析**: CoDDの問題定義（整合性破壊）を我が軍にもあると想像。karo_workaroundsを1回grepすれば「ゼロ件」と判明する事実を確認しなかった

### 教訓
- リポジトリ探索は全モジュール網羅が前提。部分読みで結論するな
- 「未実装」と判定する場合、該当モジュールの不在または空実装を確認せよ
- cli.pyのルーティング先が未読なら「未確認」と報告せよ、「未実装」と断じるな
- **外部ツールの問題定義をそのまま自システムに移植するな。自システムのデータで問題の存在を確認してから解決策を提案せよ**
- 「ギャップがある」≠「問題が起きている」。ギャップは概念上の差分であり、実害はデータで検証する

### §8.7 第6サイクル — 行動・検証・なぜの実践

> 殿指示「気づいたら行動して検証して確認してなぜを回せ」

**行動1**: CoDDのsanitization pipeline転用可能性を実データ検証
- 忍者報告(queue/reports/)でメタ解説混入("I'll...", "Let me...", "以下の...")をgrep → **ゼロ件**
- 理由: 忍者出力はテンプレートYAML。自由記述Markdownではない。テンプレート方式がメタ解説汚染を構造的に防止
- 結論: sanitization pipelineの転用は不要。テンプレート方式が同等以上の防御

**行動2**: 「完了判断が早い」根因のなぜなぜ → LG013教訓登録
