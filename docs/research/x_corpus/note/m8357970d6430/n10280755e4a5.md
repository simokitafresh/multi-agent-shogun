# お薬手帳のOCRを4段パイプラインで攻略した話

<!-- key=n10280755e4a5 publish_at=2026-05-16T16:32:26.000+09:00 price=0 full=True like=13 -->

お薬手帳をスマホで撮って、テキストにしたい
医療現場で電子カルテに情報を入力するとき、お薬手帳の内容を手で打ち直す作業があります。
患者さんが持ってくるお薬手帳をスマホで撮影して、テキストとして取り込めたら楽なのに。そう思って作り始めたのがSimple-OCRというWebアプリです。
ところが、お薬手帳のOCRは想像以上に手強い相手でした。
薬局ごとにフォーマットが違います。段組みも違う。同じ薬局でも縦向きと横向きがある。さらに厄介なのは、テキストを読み取れても「どの薬がどの用法に属するか」が分からないこと。ただ文字を読むだけでは使い物にならないのです。
この記事では、Google Vision API単独の素朴なアプローチから始めて、LLM直接投入やNDL OCR-Liteの試行錯誤を経て、最終的に4段パイプラインに辿り着くまでの過程を書きます。

Phase 1 — Google Vision APIで読み取る
最初のアプローチはシンプルでした。Google Cloud Vision APIのDOCUMENT_TEXT_DETECTIONに画像を投げて、返ってきたテキストをそのまま表示する。
文字認識の精度は高い。薬品名の「ヒルドイドソフト軟膏0.3%」も「デキストロメトルファン臭化水素酸塩錠15mg」も正確に読み取れます。速度も645msと速い。コストは1枚$0.0015（約0.2円）。
ただし、返ってくるのは生テキストです。薬局の住所、電話番号、FAX番号、服薬指導の文章、薬局のフッター文言がすべて混ざって出てくる。電子カルテに貼り付けるには余分な情報が多すぎました。
Phase 2 — 除外パターンで不要テキストを削る
そこで除外パターンマッチの仕組みを作りました。
SQLiteのデータベースに除外パターンを登録しておき、OCR結果から定型文を自動で取り除く。管理画面からパターンを追加・編集できるようにして、正規表現も使えるようにしました。
これで「ご不明な点がございましたら〜」のような服薬指導文や、薬局の連絡先は消せるようになりました。
問題は、薬局ごとにパターンが違うこと。A薬局のフッター文言はB薬局では出てこない。新しい薬局のお薬手帳を読むたびに、管理画面を開いて除外パターンを手動で追加する作業が発生しました。パターンは増え続ける一方です。
そしてもっと根本的な問題がありました。テキストからノイズを削っても、残ったテキストの構造化ができない。「アジスロマイシン錠500mg」と「1日1回 朝食後 3日分」が別々の行にあるとき、この2つが同じグループだとどうやって判断するのか。除外パターンではこの問題は解けません。
Phase 3 — LLMに画像を直接投げてみた
2024年以降、Claude VisionやGPT-4oなどのLLMが画像を直接認識できるようになりました。Google Vision APIの代わりに、LLMに画像を投げれば文字認識と構造化を同時にやってくれるのでは。そう考えて試しました。
3エンジンの比較結果はこうでした。
Google Vision API: 645ms、$0.0015
Claude Haiku (Vision): 8,223ms、$0.0044
GPT-4o mini (Vision): 12,155ms、$0.0058
速度はGoogleが13倍から19倍速い。コストも3倍から4倍安い。
肝心の精度はどうか。Google Visionが薬名や固有名詞で最も正確でした。Claude/GPTは医療用語を誤読するケースがありました。少なくともテキストの読み取り精度において、Google Vision APIは圧倒的に優秀でした。
LLMは「読む」のが得意ではない。「理解する」のが得意なのです。文字認識はOCR専門エンジンに任せるべきだと分かりました。
Phase 4 — 国立国会図書館のNDL OCR-Liteを試す
Google Vision API以外のOCRエンジンも検討しました。国立国会図書館が開発したNDL OCR-Liteは、日本語に特化したオープンソースのOCRです。レイアウト認識、読み順序決定、文字認識の3層構成で、縦書きにも対応している。CC BY 4.0ライセンスで商用利用も可能です。
実際にお薬手帳の画像を読ませてみました。
「ヒルドイドソフト軟膏」がNDL OCR-Liteでは「ヒルド、イト、ソフト軟膏」に分裂
「ロラタジンDS」が「ロラタン'ンOS」に化ける
NDL OCR-Liteは書籍や古典籍向けに最適化されています。お薬手帳のような小さい文字が密集したフォーマットには向いていませんでした。速度も2,457msとGoogle Visionの4倍近くかかります。
転換 — 読み取りと構造化を分けて考える
ここまでの試行で分かったことがあります。
テキストの読み取りはGoogle Vision APIが最強。でも構造化はできない。LLMは構造化が得意だが、テキストの読み取り精度ではGoogle Visionに負ける。
ならば、Google Visionで正確に読み取り、その結果をLLMで構造化する二段構えはどうか。
試してみました。Google VisionのDOCUMENT_TEXT_DETECTIONで座標付きブロックを取得し、そのJSONをClaude Haikuに渡して構造化JSONを出力させる。
結果は5,017ms、$0.0070（約1円）で、8薬品の構造化JSONが返ってきました。薬品名、用量、用法、日数が正確に分離されている。
問題は安定性でした。Haikuが「この薬はどのグループに属するか」を座標の数値比較で判断しようとする。「y座標350の薬はy座標400の用法に属する？それともy座標500の用法に属する？」という推論をLLMに任せると、実行のたびに結果が変わるのです。
14回の試行を繰り返しました。3回連続で同じ正解を出すことがなかなかできない。
Stage 1.5の導入 — LLMに座標推論をさせるな
なぜ不安定なのか。LLMの弱点は数値の大小比較です。座標の推論という、本来はdeterministicに解決できる問題をLLMに押し付けていた。
解決策はこうです。Pythonのregexでお薬手帳の用法テキスト（「1日2回」「毎食後」「7日分」など）を事前に検出する。検出したブロックのy座標範囲を計算して、プロンプトに注入する。
「group 0: y座標0から350の薬はこの用法に属する」「group 1: y座標351から500の薬はこの用法に属する」
こうすればLLMは座標の大小比較をしなくていい。答えが最初からプロンプトに書いてある。LLMは薬品名の分離や、ヘッダ情報の抽出という、テキストの構造化だけに専念できます。
temperature=0と組み合わせて、6種類のお薬手帳サンプルで各3回、合計18回のテストが全て同じ正解を出しました。
4段パイプラインの全体像
最終的に完成したパイプラインは4段構成です。
Stage 1: Google Vision API
画像をDOCUMENT_TEXT_DETECTIONに投げて、座標付きテキストブロックの配列を取得します。各ブロックに「何が書いてあるか」と「画像のどこにあるか」の両方が入っています。
Stage 1.5: deterministic前処理（Python）
LLMを使わない前処理です。3つのことをします。
1つ目は、不要ブロックの除去。薬局の住所やFAX番号、服薬指導の長文をregexで検出して取り除きます。ただし薬品名を含むブロックは絶対に消さない安全弁付きです。入力トークンが平均12%減り、コストと速度が改善します。
2つ目は、画像の向きの検出。ブロック座標のx方向の広がりとy方向の広がりを比べて、縦向きか横向きかを自動判定します。横向き画像ならx軸でソートし直します。
3つ目が核心で、用法ブロックの事前検出です。「1日2回」「毎食後」「かゆい時に塗布」などのパターンをregexで見つけ、座標範囲を計算してプロンプトに注入します。
Stage 2: Claude Haiku（構造化JSON出力）
Stage 1.5で整えた座標付きテキストとグルーピング境界をプロンプトに含めてClaude Haikuに渡します。temperature=0で出力を決定論的にしています。
Haikuがやるのは、テキストを構造化JSONに変換すること。患者名、処方日、クリニック名、医師名を抽出し、各薬品の名前、用量、用法をスキーマに従って出力します。座標の推論はしません。
Stage 3: deterministic整形（Python）
構造化JSONからコピペ用のテキストを生成します。LLMを使いません。
数値の「3」を「1日3回」に変換したり、メーカー名の「サワイ」「トーワ」を薬品名から除去したり。この整形ロジックをスクリプトに閉じ込めることで、不要項目の変更はStage 3だけで完結します。プロンプトを書き直す必要がありません。
なぜ4段に分けたのか
この設計には原則があります。LLMには得意なことだけやらせる。
文字を読む → Google Vision API（OCRの本業）
座標の計算 → Python regex（deterministic）
テキストの構造化 → Claude Haiku（LLMの得意分野）
整形 → Python（deterministic）
LLMが苦手な座標推論や整形ロジックはdeterministicなコードが担当します。LLMが得意なテキストの意味理解と構造化だけをLLMに任せる。
Phase 2の除外パターンマッチは、薬局ごとにパターンを手動登録し続ける運用が必要でした。Stage 1.5のregexフィルタは、「TEL」「FAX」「ご不明な点」のような汎用パターンで済みます。薬局が変わっても同じロジックが使えます。
コストは1枚あたり約$0.013（約2円）。処理時間は平均7秒。その大半はStage 2のHaiku API呼び出しです。
お薬手帳特有の工夫
お薬手帳には特有の構造があります。グループの一番下に用法が記載されている。これがグルーピングの手がかりです。
例えば、こういう並びになっています。
ヒルドイドソフト軟膏0.3% 全50g
ロコイド軟膏0.1% 0.5g
1日2回 塗布
上の2つの薬品は「1日2回 塗布」というグループに属する。用法テキストの出現位置だけでグループの区切りを判定します。処方番号ではありません。
同じ値の用法が複数箇所にあれば、それぞれ別グループです。「分3毎食後7日分」が2箇所に書いてあるなら、2つの別々のグループがある。
この「位置ベースのグルーピング」をStage 1.5のregexで事前に解決し、LLMにはグループ境界を確定情報として渡す。これが安定性の鍵でした。
まとめ
お薬手帳のOCRで試したアプローチの変遷です。
Google Vision API単独: 精度は高いが余分な情報が多く構造化できない
除外パターンマッチ: ノイズは消せるが薬局ごとにパターン追加が必要。構造化は解けない
LLM直接画像投入: テキスト読み取り精度でGoogle Visionに劣る。速度も13倍以上遅い
NDL OCR-Lite: 日本語特化だがお薬手帳の小さい文字で致命的な誤読
Google Vision + Claude Haiku二段構え: 構造化に成功。ただし座標推論が不安定
4段パイプライン: deterministic前処理でLLMの弱点を補い、安定した構造化を実現
「LLMには得意なことだけやらせる」。言葉にすると当たり前ですが、実際に試行錯誤を重ねないとどこが得意でどこが苦手かは分かりません。
座標の比較はregexでできる。テキストの整形はPythonでできる。LLMの出番は「テキストの塊から意味のある構造を取り出す」一点。その一点においてLLMは圧倒的に強い。
それぞれの道具を得意な場所で使う。Simple-OCRのパイプラインはそういう設計になっています。
