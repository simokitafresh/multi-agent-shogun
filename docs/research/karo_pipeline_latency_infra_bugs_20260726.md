## §16 受領証の読み方 — `complete=True` は全数の証明にならない（揮発層から移設・出典 blt_190155）

軍師のisolated clone面検証（固定SHA `48c96a799`）の受領証実値:

```
result=FAIL / rc=1 / complete=True
observed_test_count=2634 / declared_test_count=2634   ← 完全一致
skip_count=0 / duration=477035ms(7分57秒)
しかし START=98 / DONE=97 / selection_count=171
```

**機序**: 実行はアルファベット順。97本目 `test_insight_write` まで進み、98本目 `test_karo_snapshot_freshness` がSTART後にFAILして打ち切られた。受領証の `declared_test_count` は**「そこまでに観測したケース数」**を入れるため `observed` と**必ず一致する**。

∴ **`declared==observed` は自己整合であって何の証明にもならない。** `complete=True` も「打ち切りまで正常に処理した」の意であり「全数走った」ではない。

**主判定は `selected == executed`。`complete` は補助。**（4条件 = `selected==discovered==executed` かつ `complete==true`。ただし `complete` 単独は無力と実証済み）

**帰結**: 最初のFAILで打ち切られるため**全FAIL列挙が構造的にできない** — 是正しても次のFAILが順次現れるモグラ叩きになる。実測: 共有版(94本)とiso版(97本)でFAIL 3件の**内訳が違う**。`RUN_TESTS_FAIL_FAST` 等のgrepは**0件**で、打ち切りが設計か副作用かは**未確定**（半蔵弾のスコープ、停止時点で未着地）。

**なぜ隔離が要るか**: 共有worktreeでは走行中に他者（＝家老が配備した忍者）がtestをcommitし、`declared` を `observed` が追い越して打ち切られる。**検証と生産が同じ資源を奪い合う構造**であり、isolated cloneはその**構造分離**である。配備を止めずに全数検証できる**両立解**。

**ただし** isolated cloneは「動く標的」を解くが、**§16の「部分実行を全数と区別できない」問題は解かない**。後者を塞ぐのは範囲identity契約（主判定 `selected==executed`）である。
