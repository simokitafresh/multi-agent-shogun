【最優先指示：DM-Signal 月次リターン設計を基本原理から再整理せよ】

現在の
`dm-monthly-trade-bug-asis-tobe-5w1h_20260802.md v5.22`
は重要な調査・証跡を大量に含んでいる一方、問題解決の過程で設計そのものが複雑化している可能性がある。

ここで一度、既存実装・既存WBS・ledger・過去の仮説に引きずられず、
「月次リターンとは何か」
「リアルタイム環境では何を表示すべきか」
という基本原理から設計を再検討せよ。

目的は既存設計の否定ではない。
必要な証跡・安全策・歴史復元ロジックは保持しつつ、
本来単純であるべき計算原理と、歴史データ修復・DB移行・監査の複雑性を分離することである。

==================================================
■ 0. 今回の最重要認識
==================================================

今回の問題の本丸は、モメンタム計算そのものではない。

Standard PFのモメンタム判定は基本的に月末等の確定価格を用いており、
月次リターン境界とは別問題である。

問題の中心は、

「月次リターンをリアル環境で、いつ、どの価格を使って、どの状態で表示・確定するか」

である。

また、

「過去の確定済みデータセットを後から再計算する問題」

と

「現在進行中のリアル環境で、まだ未来の価格が存在しない状態を扱う問題」

を絶対に混同してはならない。

この2つは別問題である。

==================================================
■ 1. 基本原理：月次リターン計算そのものは単純である
==================================================

月次リターンの数学を複雑化してはならない。

本質的には、

    Return = EndValue / StartValue - 1

だけである。

PFの場合は、その期間に実際に保有している構成銘柄・weightに従って
Start→Endの価格変化を評価する。

Close系列とOpen系列を混在させない。

重要なのは計算式ではなく、

    Startは何か
    Endは何か
    その値は現時点で存在するのか
    その値は暫定なのか確定なのか

である。

複雑なロジックを計算式そのものへ持ち込むな。

==================================================
■ 2. リアル環境では「必要な未来データがまだ存在しない」
==================================================

ここを最重要事項として設計せよ。

例：

7/31(金) 市場終了
8/1(土) 暦上8月になる
8/2(日)
8/3(月) 米国市場の8月初回取引

8/1時点では、

    8/3 Open
    8/3 Close

はまだこの世界に存在しない。

したがって、

「8月の正式な境界価格が存在しないから計算不能」

という状態は当然発生する。

しかしリアルなアプリケーションとして、

    月が変わった途端にリターン表示が消える
    NULLになる
    次の市場開始まで何も表示できない

という設計も不適切である。

したがって、

★必要な確定データがまだ揃っていなくても、
  現時点で利用可能な情報による仮計算値を常に表示する。

これを pending とする。

==================================================
■ 3. pending と confirmed を第一級概念にせよ
==================================================

月次リターンには最低でも、

    pending
    confirmed

の状態を明示的に持たせる設計を検討せよ。

【pending】

正式計算に必要なデータの一部がまだ存在しない状態。

ただし表示を停止してはならない。

現時点で利用可能な最善のデータを用いて仮計算し、

    value
    status = pending
    provisional reason
    使用したstart/end
    使用したprice type
    as_of

を追跡可能にする。

【confirmed】

正式な境界・価格・holding等、
確定計算に必要な入力が揃った状態。

pendingで使用していた仮入力を正式入力に置き換え、
同じ計算原理で再計算する。

    pending → confirmed

は「別の計算方式への切替」ではない。

★同じ計算式に対して、未確定入力が確定入力へ置換されるだけ

という構造を第一候補とせよ。

==================================================
■ 4. pending専用の別計算式を作るな
==================================================

非常に重要。

pending用とconfirmed用で別々の巨大な計算ロジックを作ってはならない。

原則：

    同じreturn engine
    同じweight展開
    同じprice semantics
    同じOpen/Close系列

を使う。

違うのは、

    boundary/input certainty

だけである。

概念的には、

    calculate_return(start, end, holdings)

は一つ。

その入力に

    confirmed input

が入るか、

    provisional input

が入るかだけを変える。

これにより、

    provisional calculator
    confirmed calculator
    MTD calculator
    historical calculator

のような計算ロジックの枝分かれを極力防げ。

==================================================
■ 5. 「月が変わった」と「市場期間が開始した」を分離せよ
==================================================

calendar month rollover と market data availability は別物である。

8/1になったからといって、
8/1のOpen/Closeが存在するとは限らない。

したがって、

    calendar_month = August

と

    first tradable observation for August exists

を同一視するな。

月替わり直後の休日等では、

    calendar monthは新月
    正式な新月境界価格は未到着
    表示値はpending

という状態が正常に存在する。

これを異常扱いしない。

==================================================
■ 6. 「存在しない価格」を捏造するな
==================================================

pendingを導入するからといって、

    8/1 Openがない → 7/31 Closeを8/1 Openとして保存
    未来の8/3 Openを推測する
    存在しない営業日のprice rowを作る

等は禁止。

仮計算値と仮の市場価格は別物である。

市場価格の一次データは事実のみを保持する。

pendingとは、

「存在するデータだけを使った暫定評価」

であって、

「存在しない価格を生成する」

ことではない。

==================================================
■ 7. provisional sourceを明文化せよ
==================================================

ここは勝手に実装を決めず、まず設計案を提示せよ。

正式境界価格がまだ存在しない場合、
pending値のEnd/Startとして何を採用するかを整理する。

候補例：

A. latest available market valuation
B. 前市場日の確定Close
C. as_of時点で利用可能な最新価格
D. その他、現行UIの意味論と整合する値

重要なのは、

「とりあえずfallback」

として暗黙実装しないことである。

必ず、

    provisional_source
    provisional_as_of
    missing_requirement

が説明可能な設計にする。

そして正式データ到着時に必ず再計算されることを保証する。

==================================================
■ 8. fail-visible と pending を混同するな
==================================================

現在の設計書では fallback禁止 / fail-visible が重要原則になっている。

これは維持する。

ただし、

「未来の市場価格がまだ存在しない」

ことはfailureではない。

正常なpending状態である。

一方、

    本来存在すべきholding_signalが欠損
    configが壊れている
    weightsが空
    必須の過去価格が欠損

などはデータ異常であり、fail-visible対象。

したがって最低でも、

    PENDING_EXPECTED
    CONFIRMED
    ERROR

の意味論を分離することを検討せよ。

pendingをERROR扱いするな。
ERRORをpendingで握りつぶすな。

==================================================
■ 9. 歴史復元問題と通常運用問題を分離せよ
==================================================

現在の設計書が巨大化している最大要因の一つである。

以下は別レイヤーとして設計せよ。

[A] 通常時の月次リターン計算原理

[B] リアルタイムpending→confirmed lifecycle

[C] 過去の壊れたmonthly_returns/trade_performanceを
    正しい境界へ復元するmigration/backfill

[D] ledger / expanded weights / signalsから
    過去の実効境界を復元するhistorical resolver

[E] backup / rollback / oracle / 全数監査

A/Bは将来ずっと使う通常業務ロジック。

C/D/Eは今回の障害修復・移行・監査ロジックを多く含む。

これらを一つの「月次リターン計算仕様」に混ぜるな。

特に、

historical boundary reconstructionが複雑だからといって、
通常時のmonthly return engineまで複雑にしてはならない。

==================================================
■ 10. モメンタム計算と月次リターンを再度分離せよ
==================================================

Standard PFのモメンタム判定は、
今回のmonthly return boundary問題と原則別系統。

月次リターン境界を修正するために、
Standard PFのmomentum windowを変更してはならない。

一方、FoFは子PFのMonthlyReturn/cumulative_returnを
擬似価格として利用しているため、
monthly return修正による二次的なsignal変化はあり得る。

これは、

「モメンタム計算方式が壊れていた」

のではなく、

「FoFのmomentum inputとなる子PF系列が修正されるため結果が変わり得る」

と整理すること。

この区別を設計書の冒頭で明記せよ。

==================================================
■ 11. UI/API/DBの意味論もpending対応で再確認せよ
==================================================

以下を確認せよ。

月替わり直後に、

    UIには何を表示するのか
    APIは何を返すのか
    DBには何を保存するのか

を分けて設計する。

特に検討すべきは、

    pending値をDBへ永続化するのか
    runtime計算だけにするのか
    confirmedと同一rowを更新するのか
    status/version/as_ofを持つのか

である。

ここは現物コード・DB schema・UI callerを調査した上で案を出せ。

ただし、

★「UIに常に値が必要だからconfirmedを偽装する」

方式は禁止。

UIはpendingをpendingとして表示できる設計にする。

==================================================
■ 15. 判断原則
==================================================

迷った場合は以下を優先する。

1. 市場に存在しない価格を作らない
2. しかしリアルUIの値を不必要に消さない
3. 未確定ならpendingとして明示する
4. 確定したらconfirmedへ昇格する
5. pending/confirmedは同じ計算原理を使う
6. 正常な未到着と異常な欠損を分離する
7. historical repairを通常計算へ持ち込まない
8. momentumとmonthly returnを混同しない
9. 一次データ・status・as_of・provenanceを追跡可能にする
10. 単純な問題を既存コード都合で複雑化しない

==================================================
■ 最終ゴール
==================================================

「月次リターン」という単純な概念を、
リアルタイム運用でも単純なまま成立させること。

理想形は、

    価格・holding等が未確定
        ↓
    同一engineで provisional input により計算
        ↓
    pendingとして表示
        ↓
    正式データ到着
        ↓
    input確定
        ↓
    同一engineで再計算
        ↓
    confirmed

である。

一方、今回必要となった複雑な

    historical boundary reconstruction
    stale ledger repair
    backfill
    oracle
    backup/restore
    全数監査

は、この通常計算モデルとは別の
「migration / incident recovery layer」
として隔離する。

まずこの基本原理に照らしてv5.22を批判的にレビューし、
不要な複雑性・概念混同・通常経路へのmigration logic漏出を列挙したうえで、
ブラッシュアップ版設計書案を作成せよ。

既存設計を守ることを目的にするな。
既存設計を捨てることも目的にするな。

目的は、

「リアル環境で正しく動き、説明可能で、最小限に単純な設計」

へ到達することである。

まだ実装・起票・deployは行うな。
設計と現物調査のみ行え。
